# Конституція проєкту "Система автоматизації діяльності митного брокера (CustomsBroker)"

## Core Principles

### I. Мінімальна складність архітектурних і програмних рішень (KISS & YAGNI)
Архітектура та програмні рішення ПОВИННІ бути мінімально достатніми для реалізації навчальних завдань системи митного брокера.
- Забороняється використання надлишкових шаблонів проєктування, багаторівневих абстракцій "на майбутнє" та сторонніх фреймворків без прямої потреби.
- Кожне рішення має бути простим, прямолінійним і зрозумілим для аналізу та супроводу.
- *Обґрунтування*: Навчальний характер проєкту передбачає наочну демонстрацію фундаментальних концепцій ООП та базової предметної області без зайвого когнітивного навантаження.

### II. Принцип єдиної відповідальності (Single Responsibility Principle, SRP)
Кожен клас у системі ПОВИНЕН мати лише одну відповідальність та одну причину для зміни.
- Сутності предметної області (наприклад, митна декларація, клієнт, вантаж) не повинні займатися введенням/виведенням даних, взаємодією з користувачем чи валідацією зовнішніх форматів.
- Бізнес-логіка, збереження стану в пам'яті, перевірка коректності даних і консольне представлення повинні бути реалізовані в окремих спеціалізованих класах.
- *Обґрунтування*: Висока внутрішня зв'язність (High Cohesion) і низьке взаємопроникнення обов'язків полегшують налагодження, розуміння та тестування системи.

### III. Імітація зовнішніх операцій через консольний вивід (Console Simulation)
Замість виконання реальних зовнішніх дій (підключення до митних реєстрів, платіжних шлюзів, банківських API, відправки email тощо) методи ПОВИННІ виводити відповідні інформативні повідомлення в консоль.
- Реальні зовнішні інтеграції та мережеві виклики СУВОРО ЗАБОРОНЕНІ на даному етапі проєкту.
- Консольні повідомлення повинні чітко відображати назву виконуваної операції, сутнісні параметри та статус успішності/результат імітованої дії.
- *Обґрунтування*: Дозволяє повністю змоделювати життєвий цикл процесів митного оформлення без необхідності розгортання та налаштування зовнішньої інфраструктури.

### IV. Автономність, компіляція та запуск виключно з командного рядка (CLI Execution)
Компіляція, тестування та запуск застосунку ПОВИННІ виконуватися виключно через стандартний інтерфейс командного рядка (CLI).
- Застосунок НЕ ПОВИНЕН вимагати зовнішніх сервісів, серверів застосунків, баз даних або черг повідомлень.
- Усі дані зберігаються виключно в пам'яті (in-memory) під час виконання або в локальних текстових файлах за потреби.
- *Обґрунтування*: Забезпечує абсолютну портативність застосунку та гарантує легкість перевірки й запуску на будь-якій системі зі стандартним JDK.

### V. Контрольоване впровадження залежностей (Constructor / Setter Dependency Injection)
Впровадження залежностей (Dependency Injection, DI) ПОВИННО здійснюватися виключно через конструктори класів (рекомендовано) або setter-методи.
- Використання статичних методів для впровадження чи отримання залежностей (Static Factories, статичні Service Locator, синглтони з глобальним доступом до стану) СУВОРО ЗАБОРОНЕНО.
- Класи не повинні самостійно створювати екземпляри сервісних залежностей через оператор `new` всередині своїх методів; залежності мають передаватися ззовні.
- *Обґрунтування*: Забезпечує слабку зв'язаність компонентів (Loose Coupling), явне декларування залежностей і запобігає виникненню прихованого глобального стану.

### VI. Англійськомовний код та українськомовна документація (Bilingual Naming & Comments)
У кодовій базі встановлюється чіткий двомовний розподіл:
- Усі назви класів, інтерфейсів, методів, змінних, пакетів та констант ПОВИННІ бути англійською мовою та відповідати конвенціям найменування Java (CamelCase, PascalCase, UPPER_SNAKE_CASE).
- Коментарі до коду (Javadoc, внутрішні коментарі), пояснення, повідомлення для користувача в консолі та документація ПОВИННІ бути українською мовою.
- *Обґрунтування*: Формує культуру написання коду відповідно до міжнародних стандартів інженерії ПЗ, зберігаючи при цьому доступність і зручність сприйняття навчальних матеріалів українською мовою.

### VII. Текстовий формат UML-діаграм у каталозі docs (Text-Based UML in docs/)
Усі UML-діаграми проєкту (діаграми класів, послідовності, прецедентів тощо) ПОВИННІ зберігатися у каталозі `docs/` виключно в текстовому форматі (PlantUML `.puml` або Mermaid `.mmd` / `.md`).
- Графічні зображення (PNG, SVG тощо) НЕ ПОВИННІ бути первинним джерелом істини і можуть існувати лише як згенеровані артефакти.
- *Обґрунтування*: Текстовий формат діаграм дає змогу ефективно контролювати версії архітектурних рішень у Git (перегляд diff, рецензування змін, усунення конфліктів злиття).

### VIII. Україномовна специфікація проєкту (Ukrainian Project Specification)
Усі артефакти специфікації проєкту (конституція, специфікації вимог, плани реалізації, списки завдань, описи функцій) ПОВИННІ вестися українською мовою.
- Термінологія предметної області митної справи (митна декларація, митний брокер, митна вартість, вантаж, ставка збору, дозвільні документи) повинна бути послідовною та узгодженою в усіх документах.
- *Обґрунтування*: Забезпечує точність бізнес-вимог, усуває двозначність трактувань і відповідає мовним вимогам навчального процесу.

## Технологічний стек та обмеження середовища

- **Платформа**: Java Standard Edition (SE).
- **Збірка та виконання**: Компіляція через `javac` та запуск через `java` (або за допомогою стандартних скриптів CLI / Maven/Gradle wrapper).
- **Сховище даних**: Колекції в оперативній пам'яті (In-Memory Data Structures). За потреби — текстові файли для збереження/зчитування початкових даних. Жодних SQL/NoSQL СУБД на цьому етапі.
- **Структура проєкту**:
  - `src/` — вихідний код застосунку на Java;
  - `docs/` — текстові UML-діаграми та супровідна архітектурна документація;
  - `.specify/` — артефакти специфікацій Spec Kit і налаштування робочих процесів.

## Процес розробки та критерії якості

- **Відповідність специфікації**: Будь-яка функціональність спочатку формалізується у специфікації (`/speckit-specify`), планується (`/speckit-plan`) та розбивається на задачі (`/speckit-tasks`).
- **Контроль архітектурної чистоти**: Кожен новостворений або модифікований клас перевіряється на дотримання SRP та відсутність надлишкової складності.
- **Перевірка DI**: Усі залежності передаються виключно через параметри конструктора чи setter-методи. Жоден клас не повинен звертатися до статичних контекстів для отримання бізнес-сервісів.
- **Верифікація консольної імітації**: Усі ключові операції процесу митного оформлення повинні виводити в консоль змістовний україномовний лог подій із фіксацією вхідних даних та змодельованого статусу.

## Governance

Ця Конституція є керівним документом проєкту та має пріоритет над будь-якими іншими неформальними практиками або особистими уподобаннями щодо реалізації.

- **Процедура внесення змін (Amendment Procedure)**: Будь-які зміни або доповнення до цих принципів повинні фіксуватися у цьому файлі з відповідним обґрунтуванням, оновленням Звіту про вплив синхронізації (Sync Impact Report) та підвищенням номера версії.
- **Політика версіонування (Versioning Policy)**:
  - **MAJOR**: Зміна або скасування основоположних обмежень (наприклад, перехід від консольної імітації до підключення реальної реляційної СУБД або зовнішнього REST API).
  - **MINOR**: Додавання нових принципів, додаткових розділів або істотне розширення керівних настанов без порушення існуючих правил.
  - **PATCH**: Редагування формулювань, виправлення помилок і несемантичні уточнення тексту.
- **Перевірка відповідності (Compliance Review)**: Усі архітектурні рішення, pull request-и та етапи здачі проєкту мають проходити рев'ю на відповідність цим 8 основним принципам.
