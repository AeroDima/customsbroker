**Feature**: `001-uml-domain-model` | **Дата**: 2026-10-02

## 1. Дослідження та вибір рішень

### 1.1. Формат та структура діаграми варіантів використання (`docs/usecase.puml`)

- **Рішення**: Використати синтаксис **PlantUML** з горизонтальним орієнтуванням (`left to right direction`), рамкою меж системи (`rectangle "Система автоматизації діяльності митного брокера (CustomsBroker)"`), розділенням зовнішніх акторів (`actor`) за ролями та зв'язками асоціації (`-->`), а також зв'язками між прецедентами (`<<include>>` та `<<extend>>`).
- **Обґрунтування**:
  - PlantUML є де-факто стандартом для діаграм прецедентів завдяки багатим засобам візуального структурування меж системи та стереотипів.
  - Повністю задовольняє вимоги Конституції проєкту (Розділ VII: Текстовий формат UML у каталозі `docs/`).
  - Текстовий файл `.puml` у кодуванні UTF-8 без BOM ідеально версіонується в Git.
- **Розглянуті альтернативи**:
  - *Mermaid usecase*: Наразі має експериментальний та обмежений синтаксис для складних діаграм прецедентів, менш наочно відображає межі системи та зв'язки `<<include>>`/`<<extend>>`. Відхилено на користь PlantUML.

---

### 1.2. Синтаксис та стандартизація діаграми класів (`docs/class.mmd`)

- **Рішення**: Побудувати діаграму класів у форматі **Mermaid (`classDiagram`)** із суворим дотриманням правил ООП, сигнатур Java та конвенцій SOLID:
  - Інтерфейс: `<<interface>> IDocumentPackageHandler` з методом `+processDocumentPackage(DocumentPackage pkg) boolean`.
  - Абстрактний клас: `<<abstract>> CustomsParticipant` з полями `#id`, `#name`, `#contactEmail`, конструктором та методом `+getParticipantInfo() String`.
  - Конкретні учасники: `Importer`, `CustomsBroker`, `CustomsInspector` з наслідуванням `CustomsParticipant <|-- ...` та поліморфною реалізацією `+processDocumentPackage(...)`.
  - Сутності декларації: `CustomsDeclaration` з перевантаженими методами `+calculateDuties(double rate) double` та `+calculateDuties(double rate, double preferentialDiscount) double`.
  - Товарна позиція: `DeclarationItem` зі зв'язком строгої композиції `CustomsDeclaration *-- DeclarationItem`.
  - Довідник УКТЗЕД: `CommodityCodeRegistry` зі зв'язком залежності `CustomsDeclaration ..> CommodityCodeRegistry`.
  - 4 типи зв'язків: Наслідування (`<|--`), Реалізація (`<|..`), Композиція (`*--`), Залежність (`..>`).
- **Обґрунтування**:
  - Mermaid підтримується нативно в GitHub Markdown, більшості сучасних редакторів та дозволяє проводити повністю автоматизований синтаксичний контроль через CLI `@mermaid-js/mermaid-cli`.
  - Покриває всі вимоги специфікації (FR-004 - FR-011).
- **Розглянуті альтернативи**:
  - *PlantUML class diagram*: Могла б використовуватися, але специфікація (FR-004) прямо вимагає Mermaid (`docs/class.mmd`).

### 1.3. Синтаксис та узгодження діаграми послідовності (`docs/sequence.mmd`)

- **Рішення**: Використати **Mermaid `sequenceDiagram`** з:
  - Автонумерацією кроків (`autonumber`).
  - Чітким порядком учасників (lifelines) з українськими назвами та англійськими назвами класів: `actor Imp as Імпортер (Importer)`, `participant Brk as Брокер (CustomsBroker)`, `participant Dec as Декларація (CustomsDeclaration)`, `participant Reg as Довідник УКТЗЕД (CommodityCodeRegistry)`, `participant Insp as Інспектор (CustomsInspector)`.
  - Блоками активації (`activate` / `deactivate`).
  - Блоками альтернатив (`alt` / `else`) для сценаріїв успішної верифікації, виявлення розбіжностей у документах або призначення додаткового контролю.
  - Повною відповідністю публічним методам із `docs/class.mmd` (FR-013).
- **Обґрунтування**: Забезпечує прозору візуалізацію взаємодії об'єктів у часі, усуває розрив між статичною структурою класів та динамічним виконанням бізнес-сценаріїв.
- **Розглянуті альтернативи**: Текстовий опис сценаріїв без діаграми послідовності (відхилено, оскільки діаграма є обов'язковою згідно з FR-012).

---

### 1.4. Синтаксис та переходи діаграми станів (`docs/state.mmd`)

- **Рішення**: Побудувати **Mermaid `stateDiagram-v2`**, що фіксує життєвий цикл обробки вантажу та митної декларації:
  - Початковий стан: `[*] --> DocumentsReceived`.
  - Робочі стани: `DocumentsReceived` → `DeclarationDrafting` → `DeclarationVerified` → `InspectionAssigned` → `DutiesCalculatedAndPaid` → `CargoReleased`.
  - Стани помилок / відхилення: `Rejected` (через невідповідність документів, некоректні коди УКТЗЕД або порушення митних правил).
  - Термінальні стани: вихід у `[*]` з `CargoReleased` (успіх) та з `Rejected` (відмова).
- **Обґрунтування**: Синтаксис `stateDiagram-v2` забезпечує читабельне представлення кінцевих автоматів (FSM) та повну відповідність FR-014 та FR-015.
- **Розглянуті альтернативи**: Поєднання станів із діаграмою активностей (відхилено за принципом KISS, окрема діаграма станів точніше моделює життєвий цикл).

### 1.5. Технологія генерації та оформлення CRC-карток (`docs/crc.xlsx`)

- **Рішення**: Реалізувати автономний Python-скрипт (`scripts/generate_crc.py`) з використанням бібліотеки **`openpyxl`**.
  - Скрипт створює файл `docs/crc.xlsx` з 8 повноцінними картками (FR-017).
  - Структура кожної картки:
    - Заголовок: Назва класу (англійською) + тип сутності + україномовний опис ролі.
    - Дві колонки: ліва — "Обов'язки (Responsibilities)" згідно з принципом SRP (українською мовою), права — "Співпраця (Collaborators)" (перелік класів англійською мовою).
  - Оформлення (FR-018):
    - Корпоративна колірна гама (заголовки: насичений синій колір `#1F4E79`, білий жирний шрифт).
    - Тонкі рамки комірок (`thin borders`).
    - Автопідбір ширини колонок для запобігання обрізанню тексту.
    - Перенесення рядків (`wrap_text=True`).
- **Обґрунтування**:
  - Python 3.11 та `openpyxl` доступні в оточенні та дозволяють генерувати надійні валідні файли `.xlsx` без необхідності встановлення стороннього офісного ПЗ (MS Office, LibreOffice).
  - Скрипт може бути запущений будь-коли однією командою з CLI, що відповідає Конституції (Розділ IV).
- **Розглянуті альтернативи**:
  - *CSV формат*: Не відповідає вимозі специфікації щодо `.xlsx` та не підтримує форматування й об'єднання комірок.
  - *Java Apache POI*: Створює важку залежність на даному етапі проєкту, ускладнює CLI-пайплайн.

### 1.6. Інструменти валідації та тестування артефактів

- **Рішення**: Створити комплексний автоматизований тестовий набір:
  1. **Mermaid CLI (`@mermaid-js/mermaid-cli`)**: Компіляція `docs/class.mmd`, `docs/sequence.mmd`, `docs/state.mmd` у тимчасові SVG-файли для перевірки синтаксичної коректності (`npx -y @mermaid-js/mermaid-cli -i ... -o ...`).
  2. **PlantUML Validator (`scripts/validate_plantuml.py`)**: Автономний Python-скрипт перевірки синтаксису PlantUML, наявності акторів, меж системи, прецедентів, директив `@startuml`/`@enduml` та кодування UTF-8.
  3. **CRC Excel Validator (`scripts/validate_crc.py`)**: Перевірка структури `docs/crc.xlsx`, перевірка наявності всіх 8 сутностей, коректності заповнення обов'язків та колабораторів.
  4. **Master Verification Script (`scripts/verify_artifacts.py`)**: Головний скрипт верифікації, що перевіряє виконання критеріїв успішності SC-001 - SC-006.
- **Обґрунтування**: Забезпечує автоматичний контроль якості (Quality Gates) та незалежне тестування перед здачею артефактів.
