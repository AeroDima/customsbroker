## 1. Загальний огляд (Summary)

Метою цієї задачі є розробка комплексної архітектурної моделі предметної області системи автоматизації діяльності митного брокера (CustomsBroker). Модель фіксує бізнес-вимоги, ролі учасників, структурні зв'язки класів, динаміку взаємодій та життєвий цикл обробки вантажу.

Для реалізації сформовано технічний підхід:
1. **Діаграма варіантів використання (`docs/usecase.puml`)**: створюється мовою PlantUML, розмежовує системні межі та взаємодії трьох ключових акторів (`Importer`, `CustomsBroker`, `CustomsInspector`).
2. **Діаграма класів (`docs/class.mmd`)**: створюється синтаксисом Mermaid `classDiagram`, реалізує 8 ключових сутностей, дотримується принципів SOLID та 4 обов'язкових типів зв'язків (наслідування, реалізація інтерфейсу, строга композиція, залежність).
3. **Діаграма послідовності (`docs/sequence.mmd`)**: створюється в Mermaid `sequenceDiagram`, візуалізує наскрізний потік викликів публічних методів під час митного оформлення партії товару.
4. **Діаграма станів (`docs/state.mmd`)**: створюється в Mermaid `stateDiagram-v2`, описує повний скінченний автомат життєвого циклу декларації від подання документів до випуску або відмови.
5. **CRC-картки (`docs/crc.xlsx`)**: генеруються автономним Python-скриптом за допомогою бібліотеки `openpyxl`, містять деталізовані обов'язки та колабораторів для всіх 8 класів у відповідності до вимог оформлення та стилізації.

## 2. Технічний контекст (Technical Context)

- **Мови та формати специфікацій**: 
  - PlantUML (текстовий опис прецедентів);
  - Mermaid (текстовий опис класів, послідовності, станів);
  - Python 3.11 (скрипти генерації та валідації Excel-таблиці CRC);
  - Java SE 8+ (цільова платформа реалізації кодової бази).
- **Основні залежності**:
  - `@mermaid-js/mermaid-cli` v12 (синтаксичний рендеринг та CLI-валідація діаграм Mermaid);
  - `openpyxl` v3.1.5 (автономна генерація та аудит `docs/crc.xlsx`);
  - Python стандартні бібліотеки (`re`, `pathlib`, `sys`).
- **Сховище даних**: Локальна файлова система проєкту (`docs/`, `.specify/`, `specs/`). На цьому етапі зовнішні СУБД відсутні (відповідно до Конституції, Розділ IV).
- **Тестування та валідація**:
  - Автоматизована перевірка синтаксису через Mermaid CLI (`mmdc`);
  - Автономні скрипти валідації PlantUML (`scripts/validate_plantuml.py`) та CRC Excel (`scripts/validate_crc.py`);
  - Єдиний майстер-скрипт верифікації критеріїв успішності SC-001 - SC-006 (`scripts/verify_artifacts.py`).
- **Цільова платформа**: Кросплатформне виконання (Windows PowerShell, Linux/macOS CLI).
- **Тип проєкту**: Архітектурне моделювання, UML-специфікації та контракти даних.
- **Цілі продуктивності**: Повна генерація та валідація всіх 5 артефактів через CLI менш ніж за 10 секунд.
- **Обмеження**:
  - Суворе дотримання принципів Конституції I–VIII;
  - Усі текстові файли діаграм зберігаються в UTF-8 без BOM;
  - Повна відсутність залежностей від важкого комерційного ПЗ (MS Office тощо) для генерації артефактів.
- **Масштаб / Обсяг**: 5 артефактів у `docs/`, 8 обов'язкових модельних сутностей + допоміжні класи, 10 прецедентів, повний життєвий цикл станів.

## 3. Перевірка відповідності Конституції (Constitution Check)

*GATE: Всі 8 принципів перевірено та схвалено.*

| Принцип Конституції | Статус | Аналіз відповідності |
|---|---|---|
| **I. KISS & YAGNI** | **ПРОЙДЕНО** | Модель містить лише необхідні класи для навчальної системи митного брокера без надлишкових патернів чи важких фреймворків. |
| **II. Single Responsibility (SRP)** | **ПРОЙДЕНО** | Кожен клас відповідає за одну задачу: сутності не займаються введенням/виведенням, логіка розрахунку та класифікації чітко розмежована в CRC-картках. |
| **III. Console Simulation** | **ПРОЙДЕНО** | Усі операції змодельовані як локальні виклики методів без реальних зовнішніх мережевих інтеграцій; на діаграмі послідовності зафіксовано консольні повідомлення статусу. |
| **IV. CLI Execution** | **ПРОЙДЕНО** | Генерація Excel та валідація діаграм виконується виключно з командного рядка (`python`, `npx`). |
| **V. Dependency Injection** | **ПРОЙДЕНО** | Усі зв'язки класів передбачають передачу залежностей через конструктори або параметри методів. Статичні фабрики/синглтони з глобальним станом відсутні. |
| **VI. Bilingual Naming & Comments** | **ПРОЙДЕНО** | Усі програмні ідентифікатори (класи, методи, поля) — англійською мовою. Документація, назви прецедентів, описи в CRC та стани — українською мовою. |
| **VII. Text-Based UML in docs/** | **ПРОЙДЕНО** | Усі 4 діаграми розміщуються у `docs/` виключно як вихідні тексти `.puml` та `.mmd`. |
| **VIII. Ukrainian Project Specification** | **ПРОЙДЕНО** | Специфікація, план, дослідження, контракти та інструкції складено українською мовою з точною митною термінологією. |

```text

├── docs/                           # Цільові артефакти моделювання
│   ├── usecase.puml                # 1. Діаграма прецедентів (PlantUML)

│   ├── state.mmd                   # 4. Діаграма станів системи (Mermaid)
│   └── crc.xlsx                    # 5. CRC-картки класів (Microsoft Excel)
├── scripts/                        # Допоміжні скрипти автоматизації та тестування
│   ├── generate_crc.py             # Генератор docs/crc.xlsx на openpyxl
│   ├── validate_crc.py             # Валідатор вмісту та структури docs/crc.xlsx
│   ├── validate_plantuml.py        # Валідатор синтаксису docs/usecase.puml
│   └── verify_artifacts.py         # Майстер-скрипт перевірки SC-001 - SC-006
└── src/                            # Вихідний код Java (наступні етапи)
```

**Обґрунтування структури**: Каталог `docs/` містить безпосередньо первинні текстові моделі та CRC-таблицю відповідно до Конституції. Каталог `scripts/` забезпечує автономну повторювану генерацію та незалежну верифікацію без зовнішніх ручних дій.
